引言#

在 AI Agent 系统越来越复杂的今天，如何设计一个可插拔、可审计、可独立部署的 Agent 运行时引擎，是每个工程团队都需要面对的课题。

DeerFlow 是一个开源的 AI Agent 平台，其核心运行时引擎 Harness 位于 backend/packages/harness/deerflow/，作为一个可独立发布的 Python 包，提供了完整的 AI Agent 执行能力。本文基于该仓库的源码、设计文档和白皮书，从架构到实现细节进行全面拆解。

1. Harness 全景#

Harness 是 DeerFlow 的 Agent 运行时引擎，核心职责：

  1. 组装 LangGraph Agent — 将 lead agent 和 14 层中间件链组合成可执行的图
  2. 管理 Agent 执行生命周期 — 创建 → 运行 → 中断 → 恢复 → 清理
  3. 提供沙箱执行环境 — 安全执行 bash 命令，支持审计
  4. 提供状态持久化 — checkpointer + store，支持 memory/sqlite/postgres

关键依赖红线：app.* 可以 import deerflow.*，但 deerflow.* 绝不能 import app.*。这条红线由 CI 中强制执行的测试保证，确保 harness 包可以在任何 Python 项目中独立使用。

包结构概览#

deerflow/
├── agents/             Agent 核心工厂 + 中间件 + checkpointer
├── runtime/            Gateway 模式运行时
├── sandbox/            沙箱抽象（LocalSandbox + 安全审计）
├── subagents/          子智能体执行池
├── tools/              工具系统（内置 + MCP）
├── skills/             技能系统
├── models/             模型工厂（适配 10+ LLM provider）
├── mcp/                MCP 客户端
├── config/             配置系统
├── guardrails/         权限护栏
└── tracing/            链路追踪

2. 两种运行模式#

Standard 模式（4 进程）#

Nginx
├── Frontend (Next.js, 3110)
├── Gateway API (FastAPI, 8100)    只做 REST 入口
└── LangGraph Server (2024)        Agent 真正执行的地方
     ├── 独立的 LangGraph SDK 进程
     ├── 加载 agent → graph.astream()
     └── 通过 SSE 流式返回

Gateway 模式（3 进程）#

Nginx
├── Frontend (Next.js, 3110)
└── Gateway API (FastAPI, 8100)    嵌入 Agent 运行时
     ├── deerflow.runtime.RunManager
     ├── deerflow.runtime.run_agent()
     ├── deerflow.runtime.StreamBridge
     └── 直接 graph.astream() 之后 SSE 推送
维度 Standard Gateway
进程数 4 3
Agent 执行位置 LangGraph Server Gateway 进程内
网络跳转 Gateway → LG Server (HTTP) 无
运维复杂度 多一个进程 更简单
适用场景 开发/小规模 生产/私有化部署

Gateway 模式更适合生产部署——少一个进程、减少网络跳转。代价是 Gateway 进程的 CPU/内存消耗更高。

3. Agent 工厂链#

两层工厂分别服务于不同场景。

SDK 级工厂#

位于 agents/factory.py，纯参数驱动，不依赖 YAML 配置：

def create_deerflow_agent(
    model, tools=None, *,
    system_prompt=None,
    middleware=None,            # 完全接管
    features=None,              # 声明式 Feature Flag
    extra_middleware=None,      # @Next/@Prev 定位插入
    plan_mode=False,
    state_schema=None,
    checkpointer=None,
    name="default",
) -> CompiledStateGraph: ...

应用级工厂#

make_lead_agent() 位于 agents/lead_agent/agent.py，配置驱动，完整流程：

RunnableConfig → 解析参数 → 加载 agent 配置
  → 解析 skills → 创建模型 → 加载工具
  → 组装中间件 → 应用 Prompt 模板
  → LangGraph create_agent()

检查点不是在工厂中附着的，而是在 run_agent worker 中运行时才附加。

4. 中间件链：最核心的架构模式#

中间件在 agent 每次 LLM 调用前后和工具调用前后插入自定义逻辑。

Hook 机制#

class AgentMiddleware:
    def before_agent(self, state, runtime) -> dict | None
    def after_agent(self, state, runtime) -> dict | None
    def wrap_tool_call(self, request, handler) -> ToolMessage
    async def awrap_tool_call(self, request, handler) -> ...

14 层中间件链#

位置 Middleware 核心职责
[0] IdentityMiddleware M5 身份传播，验证 HMAC 签名
[1] ThreadDataMiddleware thread_id、sandbox 目录初始化
[2] UploadsMiddleware 上传文件注入到上下文
[3] SandboxMiddleware 沙箱容器生命周期管理
[4] DanglingToolCallMiddleware 修复"悬挂"的 ToolMessage
[5] SandboxAuditMiddleware Bash 命令安全审计
[6] ToolErrorHandlingMiddleware 工具异常捕获，防崩溃
[7] SummarizationMiddleware 长对话自动摘要
[8] TodoMiddleware Plan 模式的 TODO 管理
[9] TitleMiddleware 自动生成对话标题
[10] TokenUsageMiddleware Token 用量统计
[11] MemoryMiddleware 持久记忆注入
[12] ViewImageMiddleware 图片自动查看与描述
[13] LoopDetectionMiddleware 循环检测打断
[14] ClarificationMiddleware 澄清请求拦截（永在链尾）

@Next / @Prev 装饰器#

@Next(TitleMiddleware)
class MyCustomMiddleware(AgentMiddleware):
    pass

定位算法保证无锚点中间件插在 ClarificationMiddleware 之前， ClarificationMiddleware 永远在链尾。

5. Runtime 子系统#

主事件循环#

一个经典难题：跨线程事件循环冲突。langchain_openai 的 httpx client 使用 @lru_cache，cache key 不包含事件循环标识。client 在短生命周期的循环上创建后，其连接池 socket 绑定到已关闭的循环：

RuntimeError("Event loop is closed")

解决方案——注册长生命周期的主循环：

def submit_to_main_loop(coro_factory):
    coro = coro_factory()
    future = asyncio.run_coroutine_threadsafe(coro, _main_loop)
    return future.result()

StreamBridge 事件流#

Agent 执行的每一步通过 StreamBridge 发布到事件流，SSE 端点订阅后推送到前端：

agent.astream() → serialize() → bridge.publish() → SSE → React Query → UI

当前内存实现，未来可替换为 Redis pub/sub。

6. Checkpoint 检查点系统#

架构层级#

LangGraph CompiledStateGraph → Checkpointer ABC
  ├─ MemorySaver（内存，开发用）
  ├─ SqliteSaver（文件持久化）
  └─ PostgresSaver（数据库持久化）

存储后端对比#

后端 存储位置 内存占用 持久化
memory 进程内存 ✅ ❌
sqlite 磁盘文件 ❌ ✅
postgres 数据库 ❌ ✅

SQLite 数据在磁盘，操作系统只缓存热数据页到 page cache，可回收。InMemorySaver 才是存内存的——仅用于开发测试。

7. Checkpoint 磁盘膨胀：真实生产问题#

80GB 磁盘被 checkpoint.db 填满。根因——base64 图片数据被双重存储。

根因#

用户上传 1MB PNG → 文件存储 → base64 (~1.33MB)
  → state["viewed_images"] (~1.33MB)
  → Messages 中再存一份 (~1.33MB)
  → checkpoint.aput() 写入磁盘

总计: 1MB 图片 → ~2.7MB 占用

解决方案#

优先级 方案 难度 节省空间
P0 注入后清除 viewed_images 1 行代码 ~50%
P1 迁移到 MySQL/Postgres（TOAST） 配置+迁移 ~70-85%
P2 定期裁剪 checkpoint + VACUUM 定时任务 可变
P3 图片外存（只存引用） 中等改造 ~99.9%

8. 身份与多租户（M5）#

HMAC 签名驱动的身份透传机制。

传播路径#

Gateway Nginx → FastAPI → check_session
  → IdentityMiddleware.before_agent()
  → 验证 X-Deerflow-* headers
  → state["identity"] 注入

关键设计#

  • 子 agent 直接继承 identity，不需要重新签名 HMAC
  • 中间件通过 wrap_tool_call 拦截工具调用，按 TOOL_PERMISSION_MAP 检查权限
  • Whitelist default-deny：未注册的工具默认拒绝
  • Flag-off 兼容：ENABLE_IDENTITY=false 时跳过检查

9. 核心请求流#

用户请求 → Nginx → FastAPI Gateway
  → Middleware 链（session → auth → rate_limit）
  → create_deerflow_agent() / make_lead_agent()
  → run_agent worker（异步 Task）
  → agent.astream() 执行（中间件链递归调用）
  → StreamBridge.publish() 每个 step
  → SSE 推送 → 前端消费

中间件的递归执行顺序：

before_agent: [14] → [13] → ... → [0] → LLM
after_agent:  LLM → [0] → ... → [13] → [14]

10. 总结#

DeerFlow Harness 在架构设计上值得学习的几点：

  1. 红线隔离 — CI 强制 deerflow.* 不依赖 app.*，确保独立可复用
  2. 中间件链 — 14 层有序组装，@Next/@Prev 实现可插拔扩展
  3. 声明式 Feature Flag — RuntimeFeatures 声明式启用/禁用/替换功能
  4. Gateway 模式 — 减少进程数，简化运维
  5. M5 身份透传 — HMAC 签名驱动，Whitelist default-deny
  6. Checkpoint 优化 — 从 80GB 磁盘告警到一行代码解决双重存储

如果你也在设计 AI Agent 系统，Harness 的架构思路值得参考。
