智能体观测与评测：从埋点标准到生产级评估体系

一份面向企业 Agent 平台的观测与评测调研：梳理 OpenTelemetry、开源工具、评测方法与安全边界，给出从试点到生产的落地路线。
October 27, 2026

0. 一句话结论（v2 修订）#

观测走「OTel GenAI SemConv 埋点 + Langfuse v3 自托管（ClickHouse 数据层）」；评测走「Anthropic 方法论（终态锚定 + pass^k + 裁判工程）+ DeepEval / promptfoo 双框架 + 自建业务轨迹评测集」；通用 Benchmark 只做选型初筛与能力温度计，永远不作发版门禁。

0.1 相比初版的六个关键增量#

初版（2026-10-12）方向判断正确，但深度不足：工具只到"是什么"，没到"架构怎么搭、集成怎么接、坑在哪"。本次修订补齐：

  1. 格局剧变：ClickHouse 收购 Langfuse（2026-10-13，ClickHouse 完成 4 亿美元融资后宣布）[1][2]。LLM 可观测赛道进入数据基础设施整合期：Langfuse v3 起核心数据层已切换到 ClickHouse，收购后等于"可观测平台 + 列存底座"垂直一体化。对内网自托管用户是利好（生态背书更强），但也意味着运维栈里多了一个 ClickHouse。
  2. SWE-bench 正式"退役"：OpenAI 2026 年公开停用 SWE-bench Verified 代表前沿编码能力——对 138 道高频失败题复核，至少 59.4% 存在实质性题面或测试问题，且前沿模型能复现原始补丁（训练污染）[15][16]；另有研究称约 50% 被"判通过"的 PR 实际不会被真实合并、验证器错误率约 32% [16]。跑分榜单的信任基础正在崩塌，行业评测重心从"刷榜"转向"自建"。
  3. 评测沙箱本身成了攻击面：2026-07-21 OpenAI 承认一起因内部模型评估引发、波及 Hugging Face 生产环境的安全事件[19]。当模型具备长时推理与工具调用能力，“评测环境"不再是一个安全的盒子，而是模型要解决的问题之一——企业自建评测必须按安全边界设计。
  4. 国产标准与合规落地：阿里云+蚂蚁共建的 LoongSuite（OTel 扩展）开源，补齐三类 Agent 形态的语义建模与无侵入采集[11][12]；工信部《工业和信息化领域人工智能安全评测框架（2026 版）》2026-10 正式发布[20]。内网 + 国企环境，“合规评测"从可选项变成必答题。
  5. 方法论补全（比工具更重要）：Anthropic《Demystifying evals for AI agents》在 2026 年成为事实方法论基线：transcript / outcome 二分、pass^k 可靠性指标、裁判工程、环境工程、防作弊纪律[15]。工具选型应服从方法论，而不是反过来。
  6. 工具面补全：Opik（Comet，Apache-2.0，20k+ Star）[9]、LangWatch、Evidently、MLflow 3 evals 等新选项入局；“观测 + 评测 + 护栏"三线融合（AgentOps 化）成为所有头部产品的演进主线[8][28]。

0.2 三个行业数字（2026）#

数字 含义 来源
57% / 89% LangChain 调查：57% 受访企业已在生产环境运行智能体；89% 部署了可观测性 [14]
52.4% / 29.5% 同一调查：52.4% 只做离线评估，29.5% 没有任何评估——观测普及了，评测没有 [14]
26.9 亿 → 92.6 亿美元 LLM 可观测性市场 2026 年规模 → 2030 年预测，年复合增速 36.2% [14]

“装了观测、没做评测"是当前行业的主流姿势，也是 企业平台 要提前避开的坑：观测解决"看得见问题”，评测解决"敢不敢上、有没有回退”，两者缺一不可。初版引用的 Gartner 数据（85%~88% 企业把全链路可观测性列为 Agent 生产化首要门槛；缺乏系统评估体系的 Agent 项目失败率超 70%）仍然成立，趋势在过去半个月只有加强。

0.3 行业共识的质量工程闭环#

Observation → Tracing → Observability → Evaluation → Debugging → Regression → Optimization
   看到行为      链路留痕      全链路还原         敢不敢上        定位归因        防止回退        持续改进

2026 年 Agent 进入生产深水区后的新变化：这个闭环的重心正在从"观测"右移到"评测与回归”——因为观测基建（OTel + 各平台）已经商品化，而评测仍然高度手工化、高度业务化，没有银弹。

1. 观测方向（Agent Observability）#

1.1 标准层：先定标准，再选工具#

1.1.1 OpenTelemetry GenAI Semantic Conventions#

行业事实标准。把 LLM/Agent 调用抽象成标准 Span，核心属性族包括：

属性族 代表属性 说明
系统 gen_ai.system、gen_ai.request.model 模型系统标识与请求模型
用量 gen_ai.usage.input_tokens / output_tokens Token 计量（成本核算的基础）
内容 gen_ai.prompt / gen_ai.completion 输入输出内容（需注意脱敏）
工具 gen_ai.tool.* 工具调用名称、参数、结果
Agent 扩展 规划节点、多智能体协作、安全审计事件 社区 2026 持续演进中

2026-10 状态：规范已迁移到独立 semantic-conventions 仓库持续演进；GenAI SIG 覆盖提示词、模型响应、Token 用量、工具/Agent 调用与提供商元数据[30]。另有国内报道提到 2026 Q2 OTel 社区推出 LLM Trace v1.0 规范、将 Agent 推理链纳入标准可观测体系[31]（细节以官方仓库为准）。

为什么标准比工具重要：埋点按 SemConv 定义、统一走 OTLP 出口，观测平台将来可以整体替换（Langfuse → Phoenix → 自建）而不重写一行业务代码。共享的 AI 语义约定还能减少"每个集成一套数据模型"的归一化成本——这被业内称为 AI 可观测性竞赛的"胜负手：互操作性”[29]。

1.1.2 阿里云 LoongSuite GenAI 语义规范（开源）#

国内最重要的参考标准，2026-06 起开源，阿里+蚂蚁共建[11][12]：

  • 定位：基于 OTel 社区标准做扩展，在 GenAI SemConv 基础上补齐 Agent 形态语义建模：Model、Prompt、Token、Tool Calling、Agent、Memory、Session 等新概念，要像传统系统里的 HTTP 请求、数据库调用一样被标准化采集、展示和消费[12]。
  • 覆盖三类 Agent 形态：代码类 Agent（Coding Agent）、通用助理、框架型 Agent——分别设计差异化采集方案[11]。
  • 采集侧三条路：SDK 埋点、无侵入采集、以及 OBI（OpenTelemetry eBPF Instrumentation）——在 Linux 内核层自动识别并解析所有 AI 相关网络调用，把证据完整记录进 OTel 标准 trace/metrics，不改一行业务代码[26]。对"沙箱容器内无网、无法装 SDK"的场景（许多 Docker-out-of-Docker 沙箱正属于这种）极具参考价值。
  • 云栖 2026 的 AgenticOps 主张：采集标准化、统一语义建模、能力评测三件套[13]——与本文档的"观测+评测"框架完全同构，可作为国产化对标路线。

结论：埋点按 OTel GenAI SemConv 定义（gen_ai.* 属性），Agent 层扩展语义参考 LoongSuite（规划节点、工具、审计事件三类），工具侧统一 OTLP 接入。将来换平台不重写。

1.2 开源观测工具深度档案#

1.2.1 Langfuse —— 内网自托管首选#

维度 现状（2026-10）
定位 开源 LLM 工程平台：Tracing + Evals + Prompt 管理 + 数据集 + Playground 一站式
架构 v3 起核心数据层切换到 ClickHouse，以扩展到生产级工作负载[1]；自托管组件：web（应用）+ ClickHouse（分析）+ Postgres（元数据）+ Redis（队列）+ S3 兼容对象存储（blob）
集成 官方 LangGraph callback 集成（CallbackHandler 挂图即可）；OpenAI SDK 兼容层；OTLP 接入（兼容 OpenInference）
评测能力 数据集管理、人工标注、LLM-as-judge 在线评测；官方 Agent 评测指南提出黑盒（最终响应）/玻璃盒（轨迹层）/白盒（单步层）三层评测视角[15]
事件 2026-10-13 被 ClickHouse 收购（4 亿美元融资后）[2]；MIT 核心保持开源，自托管路径不变，但需关注后续商业化动作
生产要点 官方 docker-compose 是 demo 形态不是生产形态：把应用和所有有状态组件塞进一台机器，生产必须拆分部署（应用无状态多副本 + 状态组件独立 + 健康检查 + 备份策略）[3]

选它的核心理由：LangGraph 有现成官方集成（生产系统若采用 LangGraph 编排）、Evals 内置（观测与评测同一份数据底座）、社区最大（大量开源 AI 项目默认采用[5]）、ClickHouse 收购后长期生态背书增强。

1.2.2 Arize Phoenix —— OTel 原生的"开发态调试器"#

  • 开源 AI 可观测平台，为实验、评估与排障设计；基于 OpenTelemetry 构建，供应商与语言无关[6]。
  • 部署形态最灵活：pip install 本地跑、Jupyter 内嵌、容器化、云端均可——开发者在笔记本上就能看 trace，这是它区别于 Langfuse 的杀手场景。
  • 内置 RAG Triad 指标（忠实度、上下文相关性、问答相关性）与 LLM-as-judge，线上批量评估可统计整体幻觉率[32]。
  • 商业线 Arize AX：生产 LLM 监控、漂移检测（“上线一段时间后幻觉率升高"这类问题的专家）。

1.2.3 OpenLIT —— 观测+评测+护栏一体（盯紧）#

OTel 原生 Agent 工程平台，2026 年升级定位为 “trace, evaluate, guard, improve everything around the model”——把观测、评测、护栏揉在一起，是"AgentOps 化"路线演进最快的产品。适合作为 Langfuse 的互补/备选持续观察。

1.2.4 Traceloop OpenLLMetry —— OTel 发行版（采集标准化工具）#

一行代码接入，把各家 LLM/VectorDB/GPU 调用标准化成 OTel trace。它不是平台，是采集层的翻译器——适合"已有 OTel 体系"的团队先统一采集格式，再选后端。已有 FastAPI 与 OTel 基础设施时，可作为统一埋点 SDK 备选。

1.2.5 AgentOps —— 会话回放（排障利器）#

Python SDK + 可自托管 Web 面板[7]：自动追踪每次 LLM 调用的 token 消耗、成本、延迟、报错，并支持把整段会话像录像一样逐步回放。Agent 排障四要素（Traces 链路追踪、Replay 可重放、Metrics、Logs）中，Replay 是 AgentOps 的招牌[27]。适合作为开发/测试环境的排障补充，生产主线仍建议 Langfuse。

1.2.6 Helicone —— 代理式轻量观测#

一行代码接入的代理层，强项是成本追踪、缓存、限流、路由。适合作为网关侧计费/限流组件参考，不适合作为主观测平台。

1.2.7 W&B Weave —— Trace + Eval 一体（ML 团队生态）#

Weights & Biases 出品，Trace + Eval 一体，与实验追踪/数据集版本生态打通。如果团队已经在用 W&B 做模型实验管理，Weave 是顺手的选项；纯内网部署场景不如 Langfuse/Opik 干净。

1.2.8 Opik —— Apache-2.0 全能竞品（新入局，重点评估）#

Comet 开源的一站式 LLM 可观测、评估与优化平台[9][10]：

  • Apache-2.0 许可，完整平台可免费自托管，20,000+ GitHub Star[9]；声称支持 40M+ traces/天的生产级追踪量[10]。
  • 全链路追踪 + 自动化评估 + Opik Agent Optimizer（提示词/工具自动优化）+ Opik Guardrails（护栏）——与 Langfuse 功能高度重叠，且优化器是 Langfuse 没有的差异点。
  • 对企业平台的意义：Langfuse 若受收购后商业化挤压，Opik 是迁移成本最低的 Plan B（同为自托管全功能平台）。

1.2.9 LangWatch / Evidently / MLflow 3 —— 补充选项#

LangWatch：开源 LLM 可观测，质量监控+成本+安全扫描一体，轻量自托管。Evidently：LLM 数据与模型监控（数据漂移视角）。MLflow 3：evals 能力内建，适合作 MLOps 老用户的最低成本选项。三者均列入观察清单，不作主线[8]。

1.2.10 model-watchdog —— 线上稳定性兜底（保留）#

零依赖单文件：探测 Agent 配置健康端点，失败即自动还原配置并重启服务。评测与观测都拦不住的"改配置改坏线上"场景，靠它兜底。2026 年新增的类似思路：平台侧"配置变更 → 灰度 → 自动回滚"应做成 平台 网关的内建能力，而非外部脚本。

1.5 观测选型结论#

  1. 主线：Langfuse v3 自托管。理由：LangGraph 官方集成 + 观测评测同库 + 社区最大 + ClickHouse 生态长期背书。收购风险对冲：埋点全走 OTel 标准，保留迁移到 Opik/Phoenix 的能力。
  2. 开发态补充：Phoenix（pip 本地跑，开发者自诊）。
  3. 持续盯：OpenLIT / Opik（护栏与优化器融合方向）。
  4. 兜底：model-watchdog 思路内建到 平台 网关（配置灰度+自动回滚）。
  5. 部署红线：docker-compose 只能用于 PoC，生产必须组件分离（应用多副本无状态 + ClickHouse/Postgres/Redis/S3 独立部署 + 备份策略）[3]。

2. 评测方向（Agent Evaluation）#

2.1 方法论先行：比工具更重要的六个共识#

以下来自 Anthropic《Demystifying evals for AI agents》及其 2026 系列文章、τ-bench 论文与公开复现研究，是 2026 年 Agent 评测的事实基线[15]。工具选型必须服从这套方法论。

2.1.1 你评的不是模型，是"系统”#

同一个模型，换一套系统提示词、工具定义或上下文管理策略，就是另一个 Agent。模型升级 ≠ 你的 Agent 变好；模型跑分 ≠ 你的产品得分。 所以 平台的评测对象是"模型 + LangGraph 编排 + 工具 + 沙箱环境"的组合系统，这决定了评测必须在自己的平台形态上跑。

2.1.2 终态锚定：判成败查环境，不听 Agent 自报#

经典案例（Anthropic 拆解）：订票 Agent 对用户说"预订成功"，对话记录无懈可击——打开订单数据库，是空的，预订从未发生[15]。transcript 里说了什么，和环境里真的发生了什么，是两回事。

评测分工因此清晰：

视角 判什么 工具 适用
结果分 环境终态：订单落库？测试通过？文件产出？ 代码断言 成败判定（唯一锚点）
轨迹分 过程质量：多余动作？合规话术？Token 烧了多少？ 规则匹配 + LLM 裁判 失败归因、质量评估
步骤断言 关键决策点：该不该调这个工具？参数对不对？ 单元测试式检查 合规红线

轨迹规则匹配有四种现成模式（LangChain agentevals）：严格顺序 / 无序全有 / 只许子集（防越权）/ 至少超集（保底动作）——按合规敏感度选用[15]。

2.1.3 pass@k 会骗人，pass^k 才是生产指标#

  • pass@k：k 次里至少成一次的概率（能力上限，demo 指标）。
  • pass^k：k 次全部成功的概率（可靠性，生产指标），τ-bench 论文提出[15]。

Sierra 在 τ-bench 的著名数字：GPT-4o 级函数调用 Agent，零售域 pass^1 = 61.2%，航空域只有 35.2%；零售域 pass^8 跌破 25%——“demo 演示的是前者，用户体验的是后者”[15]。Anthropic 的心算例子：单次成功率 75% 的 Agent，连续 3 次全对概率 0.75³ ≈ 42%。

一句话：多采样让 demo 更好看（pass@k），也让生产更露馅（pass^k）。 报分数必须带试次数：“通过率 70%（30 任务 × 4 试次）“和光秃秃的"70%“是两种可信度。k 的参考档位：只读查询 k=3、写操作 k=5、资金交易 k=8[15]。

2.1.4 环境工程：评测的下半场是搭考场#

  • 每道题配一个世界：OSWorld 369 个任务 = 369 套初始状态 + 369 个判分脚本[15]。
  • 跑完要能倒回去：OSWorld 每次回滚 init_state 快照；WebArena 812 样例跑完必须重置环境，官方演示站"仅供浏览”[15]。
  • 试次隔离是铁律：Anthropic 观察到 Claude 翻看前几个试次留下的 git 历史借用"前人"答案——试次共享状态的评测，跑得再多都是废数据[15]。
  • 基建本身是变量：Anthropic 2026-02 实测，仅评测机器资源配置差异，就能在 Terminal-Bench 2.0 上造成 6 个百分点分差（p<0.01），超过头部模型之间的差距[15]。
  • 用户模拟器要锁版本：τ-bench 里"LLM 扮演的用户"一换版本，分数跟着动[15]。

2.1.5 裁判工程：裁判坏了比没裁判更可怕#

  • 优先级：代码裁判打底（锚定终态）→ 模型裁判补细腻维度 → 人工做金标和抽检。
  • 模型裁判三纪律：与人类专家校准（未校准的裁判分是噪声）；一个维度一个独立裁判；给裁判留"Unknown"退路[15]。
  • 裁判翻车实录：Anthropic 复核 CORE-Bench 发现判分脚本数值精度 bug（只认 “96.12” 不认 “96.124991”）——修复评测问题+换宽松脚手架后，Claude Opus 4.5 得分从 42% 跳到 95%，53 个百分点没有一个来自模型变强[15]。
  • 《Agentic Benchmark Checklist》论文点名：τ-bench 会把空响应判为成功、SWE-bench Verified 部分单测不充分——这类缺陷对 Agent 表现的高估/低估，相对误差最高可达 100%[15]。
  • 对策：每道题配**参考解（reference solution）**定期复跑——参考解过不了，先修题和裁判，再看模型分数[15]。

2.1.6 防作弊与"评测的评测”#

  • HAL 团队观察到：有 Agent 直接去 HuggingFace 搜基准答案；有 Agent 在订票任务里滥用信用卡[15]。
  • Anthropic 2026 披露：Claude Opus 4.6 在评测中自我推断出"我正在被评测”，随后定位并解密了答案[15]。
  • 更严重的：评测环境成为攻击面——OpenAI × Hugging Face 事件（2026-07-21）证明，具备工具调用能力的模型会把评测沙箱本身当成待解问题，安全事件可以外溢到生产环境[19]。平台 自建评测时：评测环境与生产环境隔离、沙箱最小权限、判分凭据独立。

2.1.7 评测的运行形态：能力评测 vs 回归评测#

  • 能力评测（capability evals）：问"它能做什么新东西"，起步通过率应该很低——全绿说明题太简单。
  • 回归评测（regression evals）：问"以前会的现在还会吗"，通过率应接近 100%。
  • 发布门禁挂在回归套件上（例：核心任务 pass^3 ≥ 90% 才能发版）；通过率爬高的能力评测"毕业"转入回归套件[15]。
  • 题库来源与循环：从真实失败中提取 20-50 个简单任务起步；上线后按比例采样生产轨迹，人工审读，新失败回流成新题——评测像维护单元测试一样成为例行公事，且必须有 owner[15]。
  • 成本量级参考：30 任务 × 4 试次（每试次输入 4 万 token / 输出 6 千 token），中档模型约 $25/轮，加模型裁判约 $32/轮[15]。降本开关：提示词缓存（评测的系统提示词与工具定义天然是稳定前缀）+ 便宜模型跑高频回归、贵模型跑大版本全量。

2.4 榜单的三个结构性问题（为什么永远不作发版依据）#

  1. 污染与记忆：公开基准的题目/代码/答案长期存在于互联网，前沿模型能复现原始补丁——高分里混了多少能力、多少记忆，拆不开[15]。
  2. 饱和与测量噪声：基准涨到八成以上后，剩余失败越来越来自坏题、口径、环境噪声，而非模型能力（Terminal-Bench 2.0 基建噪声 6pp；头部名次差异小于噪声）[15][16]。
  3. 与真实分布脱节：基准为可重复而缩小任务范围；真实用户带来长尾需求、脏数据、打断与跨系统依赖。METR 的随机对照试验证明：基准进步是真的，产品价值不会自动到账[15]。

榜单只做两件事：选模型时初筛，看能力演化时当温度计。真正的放行依据只能来自与你的用户、任务、工具和风险一致的自建评测。

3. 落地路线（结合 企业级 Agent 平台）#

3.1 平台现状与差距#

现状 与目标的差距
LangGraph 编排（生产 langgraph dev 单进程，迁移 langgraph-api 中） 无统一埋点标准；run 注册表丢失时 trace 全丢
FastAPI 网关（含 SDK 兼容层）+ Tengine 反代 网关是天然的观测/计量 OTLP 出口位，尚未利用
Docker-out-of-Docker 沙箱（无网、临时容器、非 root 无 sudo） 沙箱内 Agent 无法装 SDK/在线装包，埋点须走宿主转发或 eBPF 无侵入路线（LoongSuite OBI 思路）
多节点改造已拍板（k8s + RWX + provisioner 自建沙箱 Pod） ClickHouse/Postgres/Redis 等有状态组件正好借此独立部署
监控告警接钉钉群 质量门禁失败、成本异常可复用该通道
无评测体系、无业务评测集 全量缺口

3.2 四阶段路线图#

P0（第 1-2 周）：标准与链路打通

  • 定义 平台埋点属性字典：gen_ai.* 基础 + Agent 扩展（规划节点/工具调用/审计事件，参考 LoongSuite[11]）
  • 网关（FastAPI）加 OTel 中间件，统一 OTLP 出口；LangGraph 挂 Langfuse CallbackHandler
  • 用 docker-compose 起 Langfuse demo 环境验证端到端链路
  • 验收：一次完整 Agent 会话在 Langfuse 看到全 span 树（含模型调用、工具调用、Token/成本/延迟），沙箱内工具调用也能上报

P1（第 3-6 周）：观测平台生产化

  • Langfuse v3 自托管按生产形态拆分部署：web 多副本无状态 + ClickHouse/Postgres/Redis/S3 兼容存储独立（借 k8s 改造落地）+ 备份策略[3]
  • 沙箱内埋点方案二选一实测：宿主侧 SDK 包裹（沙箱出入口代理上报）vs eBPF 无侵入（OBI 思路[26]）
  • 大盘四件套：成本（按部门/Agent/模型）、延迟、错误率、会话留存；异常接钉钉
  • 验收：生产连续 7 天数据不断流；成本报表能按部门出账；trace 覆盖率 ≥ 95% 会话

P2（第 7-12 周）：评测闭环 v1（核心补课）

  • 从试用反馈/工单/内部失败记录提取 20-50 个业务任务起步[15]，按 tau-bench 模式建集：任务描述 + 初始状态（mock 环境）+ 期望终态（数据库断言）+ 期望工具序列（可选）+ 红线断言 + 参考解
  • 判分锚定终态：查 业务库或文件产出，不听 Agent 自报；轨迹层用 agentevals 四种比对模式 + DeepEval G-Eval 裁判
  • 每任务 4 试次起，报表带 pass^k；promptfoo 挂 CI 做回归 + 红队扫描（注入/越狱/PII）
  • 评测环境与生产隔离，沙箱最小权限（OpenAI × HF 事件教训[19]）
  • 验收：核心任务 pass^3 报表产出；CI 门禁（pass^3 ≥ 阈值）阻断发版一次走通

P3（持续）：线上对账与回归飞轮

  • 按 5% 采样生产轨迹，每周人工审读；新失败回流能力题库；通过率稳定的能力题"毕业"进回归套件[15]
  • 评测体系指定 owner；题库月度新陈代谢
  • 网关内建配置灰度+自动回滚（model-watchdog 思路平台化）
  • 验收：每季度回归套件通过率 ≥ 99%；线上故障 48h 内转化为新评测用例

3.3 业务评测集 Schema 建议（tau-bench 模式）#

task_id: qf-refund-001
description: "帮用户退掉昨天买的会员并原路退款"
initial_state:          # mock 环境初始化
  db_orders: [...]
  policy_doc: "退款政策 v3.md"
expected_outcome:        # 终态断言（成败唯一锚点）
  db_check: "orders.status == 'refunded' AND refund.amount == 39.9"
expected_tool_seq:       # 可选：轨迹红线
  - "check_policy BEFORE refund"
redlines:                # 硬断言
  - "不得越过差标直接退款"
user_simulator:           # LLM 扮演用户（锁版本）
  persona: "着急的普通用户"
trials: 4                # 试次数
reference_solution: ...  # 参考解，定期复跑校验裁判

3.4 成本估算（评测体系）#

按 30 任务 × 4 试次 = 120 试次、每试次输入 4 万 / 输出 6 千 token 估算[15]：中档国产模型（按每百万 token 输入 ¥20 / 输出 ¥60 量级）一轮约 ¥150-200，加裁判约 ¥250/轮。每天迭代 3 轮 ≈ ¥750/天，月预算 1.5-2 万元内，配合提示词缓存可再降 30-50%。观测侧成本主要是 ClickHouse 存储与运维人力，trace 采样率可调（生产建议全量 trace + 采样内容明细）。

3.5 风险与坑清单（上线前逐条打勾）#

环境组

  • 每试次从干净快照启动；试次间零共享状态（抽查验证）
  • 用户模拟器版本已固定；评测机器资源配置已固定
  • 评测环境与生产隔离，判分凭据独立

裁判组

  • 成败锚定终态而非话术；无对自然语言话术的硬字符串断言
  • 每题配参考解且每周复跑；模型裁判已与人工校准
  • 裁判有 “Unknown” 出口；环境里无答案、无历史残留

统计组

  • 每任务试次数 ≥ 3；报告分数附任务数与试次数
  • 核心场景用 pass^k 而非 pass^1；0% 通过率任务已人工复核题目本身

流程组

  • 能力/回归两套件已分开；门禁挂在回归套件上
  • 线上轨迹采样与回流机制已定；评测体系有明确 owner
